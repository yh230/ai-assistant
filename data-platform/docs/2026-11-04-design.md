## 1. 背景与定位

ai-assistant 已有 `system_db`、`hospital_db`、`registration_db`、`chat_db` 四个业务库，并通过 Kafka 发布预约域事件与审计事件，但缺少面向管理与运营的数据平台。

本项目定位为 ai-assistant 的**下游数据平台**：

- 以只读方式接入业务库，不反向写业务库，不修改 ai-assistant 现有服务。
- 补充历史数据回填能力，同时消费现有 `ai.registration.event` 实时事件。
- 在 ClickHouse 内完成 ODS / DWD / ADS 分层建模。
- 提供元数据管理、数据质量、告警闭环与运营大屏。
- Flink 仅交付作业代码，作为实时聚合的扩展方案，不参与本轮运行验证。

该项目是 Python 技术栈的数据工程项目，不以复刻 Java 微服务为目标。

## 2. 目标与非目标

### 2.1 目标

- 建立可独立演进的 `data-platform` 代码工程，后续可整体拆出为独立仓库。
- 支持 MySQL 多库全量 + 增量抽取，按水位断点续跑。
- 消费 ai-assistant 现有预约事件，与本平台抽取的 ODS 数据统一入仓。
- 在 ClickHouse 内实现 ODS、DWD、ADS 三层模型与幂等去重。
- 实现元数据浏览、6 类标准质量规则（另支持自定义 SQL）、质量评分、告警中心与 Webhook 通知。
- 提供 1920×1080 运营大屏与治理后台，支持无基础设施时的前端 mock 预览。
- 交付 PyFlink 实时聚合作业代码、Flink SQL 与部署说明，状态如实标注为未部署验证。

### 2.2 非目标

- 不下载、不安装、不启动 Kafka、ClickHouse、Flink。
- 不执行连接真实 Kafka / ClickHouse 的集成测试与端到端测试。
- 不实现 Oracle / SQLServer 适配器；数据源接口预留扩展点。
- 不实现字段级血缘图、调度 DAG 引擎、多租户隔离。
- 不在 ODS / DWD / ADS 中保留患者姓名、手机号、身份证号、聊天正文。
- 不引入 Redis、Celery 或独立任务队列。

## 5. 数据流与分层

### 5.1 接入方式

采用混合接入：

1. **历史回填**：Extractor 从 MySQL 四个库抽取，首次全量、后续按 `update_time` 增量，发送到 Kafka `dp.ods.<db>.<table>`。
2. **实时事件**：Consumer 同时订阅 ai-assistant 现有 `ai.registration.event`，用于预约创建、取消、退费、过期等实时计数。
3. **统一入仓**：两类数据最终进入 ClickHouse ODS，实时事件只作为补充，不替代历史回填。

### 5.2 数据分层

| 层 | 表 | 说明 |
| --- | --- | --- |
| ODS | `ods_registration`、`ods_chat_session`、`ods_chat_message`、`ods_doctor_schedule`、`ods_number_source`、`ods_hospital`、`ods_department` | 原始行 + 采集元数据，已脱敏 |
| DWD | `dwd_registration`、`dwd_ai_session`、`dwd_ai_message`、`dwd_schedule`、`dwd_hospital`、`dwd_department` | 清洗、枚举标准化、维度关联 |
| ADS | `ads_hospital_daily`、`ads_department_daily`、`ads_ai_daily`、`ads_pipeline_health`、`ads_quality_daily`、`ads_realtime_registration_5m` | 大屏与告警直接查询；`ads_realtime_registration_5m` 仅由 Flink 作业写入 |
| OPS | `ops_quarantine`（按 `batch_id` 去重）、`ops_ingest_audit`、`ops_registration_event` | 脏数据隔离、采集审计、实时预约事件落地 |

去重策略：ODS 使用 `ReplacingMergeTree(_ingested_at)`，以业务主键 + 来源排序；ADS 查询使用 `FINAL` 或 `argMax` 取最新版本。

### 5.3 指标定义

| 指标 | 口径 |
| --- | --- |
| 挂号量 | `registration` 按 `schedule_date` 统计 |
| 支付金额 | `sum(pay_amount)`，仅统计已支付 |
| 取消率 | `status in (4,5,6)` / 总挂号量 |
| 就诊转化率 | `status = 3` / `status in (2,3)` |
| 号源利用率 | `doctor_schedule.registered_count / total_limit` |
| AI 会话量 | `chat_session` 按 `session_type` 分组 |
| AI 消息量 | `chat_message` 按 `role` 分组 |
| RAG 引用率 | RAG 会话中 `reference_json` 非空的 assistant 消息 / RAG 会话 assistant 消息 |
| 质量分 | 规则按严重级别加权后的通过率 |
| 链路延迟 | 当前时间 - 最新 `_ingested_at` |
| Kafka 积压 | 消费位点与最新位点差值 |

## 6. 模块设计

### 6.1 数据源与元数据

- 数据源 CRUD、连接测试、库表 introspection。
- 密码使用 Fernet 对称加密存储，密钥来自 `DP_SECRET_KEY`，接口不返回明文。
- 元数据包含表名、表注释、字段名、类型、可空、字段注释、字段顺序。
- 数据源驱动通过 `db_type` 注册表解析，V1 只实现 MySQL，预留 Oracle / SQLServer。

### 6.2 同步任务与 Extractor

任务配置：源库表、目标表、主键、水位字段、水位类型（datetime / numeric）、批量大小、重叠窗口、cron、启用状态。

- 全量：按主键 keyset 分页，每批提交后记录进度；全量完成后写入水位。
- 增量：`watermark >= last_watermark - overlap_seconds`，读取上限为当前最大水位；提交成功后推进水位。
- 同一任务加数据库行级互斥标记，防止并发重跑。
- 失败重试采用指数退避；连续失败写入运行记录并触发告警。
- 运行记录包含读取行数、写入行数、耗时、错误摘要、checkpoint。
- 运行入口：`python -m etl.extractor` 由 APScheduler 触发或手工执行；`python -m etl.consumer_main` 作为常驻进程独立运行。

### 6.3 Kafka 接入

- 抽取事件 Topic：`dp.ods.<db>.<table>`。
- 事件信封复用 ai-assistant 约定：`eventId`、`eventType`、`occurredAt`、`payload`。
- 分区键优先使用 `hospital_id`，缺失时使用业务主键，保证同院数据有序。
- Producer：`acks=all`、幂等开启、批量发送、lz4 压缩。
- Consumer group：`dp-ods-loader`；手动提交位点；ClickHouse 写入成功后提交。
- 消费失败最多重试 3 次，仍失败写入 `dp.ods.DLT` 并告警。
- 通过 `eventId` 与 ClickHouse `ReplacingMergeTree` 双重保证幂等。

### 6.4 Consumer 与清洗

- 批量拉取后按分区并行处理，线程数可配置，队列有界。
- 清洗内容：去空格、类型转换、日期标准化、枚举映射、必填校验、数值范围校验。
- 脱敏规则：
  - 患者姓名、手机号、身份证号：不进入 ODS，使用掩码或哈希替代。
  - 聊天正文：只保留长度与是否有引用，不保留原文。
- 无法转换的行写入 `ops_quarantine`，记录来源、原因、样本和批次。
- 批次写入 ClickHouse 失败时不提交 Kafka 位点，触发重试与背压。

### 6.5 数据质量

标准规则类型 6 类，另支持自定义 SQL 扩展：

| 类型 | 说明 |
| --- | --- |
| NOT_NULL | 指定字段空值数 |
| UNIQUE | 指定字段重复数 |
| RANGE | 数值越界数 |
| ENUM | 枚举值非法数 |
| FRESHNESS | 最新数据时间与当前时间差值 |
| VOLUME | 当日行数与近 7 日均值偏差 |
| CUSTOM_SQL（扩展） | 自定义 SQL 返回异常行数 |

执行流程：调度触发 → 生成只读 SQL → 在 ClickHouse 执行 → 结果写入 `dp_quality_result` → 计算质量分 → 触发告警规则。

质量分按严重级别加权：P0 权重 3、P1 权重 2、P2 权重 1。

### 6.6 告警

告警指标：链路延迟、数据时效、质量分、量级异常、Kafka 积压。

- 告警规则支持操作符、阈值、窗口、连续周期、冷却时间、接收渠道。
- 指纹由规则与维度组成，冷却期内相同指纹不重复通知。
- 告警生命周期：`OPEN → ACKED → CLOSED`。
- 通知渠道：平台内告警中心 + 通用 Webhook（飞书/钉钉兼容 JSON）。
- Webhook 失败只记录日志，不回滚告警记录。

### 6.7 大屏与治理后台

- 大屏 `/screen`：深色 1920×1080，自动缩放，ECharts 图表，SSE 每 5 秒推送。
- 大屏内容：6 个 KPI + 近 30 天趋势 + 医院排行 + 科室 TOP10 + 来源分布 + AI 会话类型 + 质量分 + 实时告警。
- 治理后台：数据源、同步任务、运行记录、元数据浏览、质量规则、质量结果、告警中心。
- 前端提供 `VITE_USE_MOCK=true` 模式，使用本地 JSON 夹具预览页面；mock 数据不作为数据正确性证据。
- 登录复用 ai-assistant 登录接口，前端通过 `VITE_AUTH_BASE_URL` 指向网关。

### 6.8 Flink 代码展示位

- 作业：消费 `ai.registration.event`，5 分钟滚动窗口，按医院与事件类型聚合，JDBC sink 到 `ads_realtime_registration_5m`。
- 交付物：PyFlink 作业、Flink SQL、Dockerfile、README。
- README 与验收报告必须标注：**代码已实现，未部署、未运行验证**。

### 7.2 ClickHouse 表

代表性 DDL：

```sql
CREATE TABLE ods_registration (
  id UInt64,
  registration_no String,
  hospital_id UInt64,
  department_id UInt64,
  doctor_user_id UInt64,
  schedule_date Date,
  period UInt8,
  patient_name_masked String,
  patient_phone_masked String,
  source_type UInt8,
  pay_status UInt8,
  pay_amount Decimal(10, 2),
  status UInt8,
  create_time DateTime,
  update_time DateTime,
  _event_id String,
  _source String,
  _ingested_at DateTime
) ENGINE = ReplacingMergeTree(_ingested_at)
PARTITION BY toYYYYMM(schedule_date)
ORDER BY (hospital_id, schedule_date, id)
TTL toDateTime(schedule_date) + INTERVAL 2 YEAR;
```

ADS 表按 `metric_date` 分区，按 `(hospital_id, department_id)` 排序；质量与链路指标写入 `ads_pipeline_health`、`ads_quality_daily`。

OPS 层：`ops_quarantine` 以 `(source_table, _event_id, batch_id)` 为去重键，`batch_id` 标识隔离批次，重放批次合并而非重复；`ops_ingest_audit` 按批次记录采集审计；`ops_registration_event` 保存 `ai.registration.event` 实时事件（事件标识、医院、就诊日期、时段）。`ads_realtime_registration_5m` 仅由 Flink 作业写入。

## 9. 关键机制

- **幂等**：Kafka `eventId` + ClickHouse 主键去重；重复消费不产生重复指标。
- **断点续跑**：任务水位与运行 checkpoint 分离，失败后从上次成功批次继续。
- **背压**：有界队列 + 批量写入；ClickHouse 写入失败时暂停消费，避免内存堆积。
- **Schema 漂移**：元数据采集发现新增字段时记录差异；缺失必填字段任务快速失败，新增字段进入 `_raw`。
- **时间口径**：统一 Asia/Shanghai；按业务日期分区，跨天任务以源表业务时间字段为准。
- **日志**：结构化日志携带 `run_id`、`task_id`、`event_id`；不打印敏感字段。
- **异常分类**：连接失败、数据质量失败、写入失败、配置错误分别记录，重试策略不同。

## 11. 验证口径

### 11.1 本轮可验证

- 纯逻辑单元测试（环境已安装 pytest 时）：清洗、水位计算、质量 SQL 生成、告警去重、事件信封。

- PyFlink 作业提交与运行。
- 真实数据端到端指标与 SSE 推送。
- 性能、吞吐、资源占用。

## 13. 风险与约束

| 风险 | 应对 |
| --- | --- |
| Kafka / ClickHouse 未运行，无法证明端到端 | 端口与 Fake 支持单测；验收报告区分“已实现未验证”；提供人工验收清单 |
| 客户端库 API 变化 | 固定依赖版本；适配器层隔离，业务层不直接依赖客户端 |
| ClickHouse 去重理解偏差 | ODS 用 `ReplacingMergeTree`；ADS 查询用 `FINAL` 或 `argMax` |
| 事件覆盖不足 | `ai.registration.event` 只覆盖非匿名预约；历史与全量数据由 MySQL 回填补齐 |
| JWT 耦合 ai-assistant | 通过 `JWT_SECRET` 环境变量解耦；只校验 staff 身份，不做细粒度角色 |
| 数据隐私 | 姓名、手机号、身份证、聊天正文不落仓；日志不打印敏感字段 |
| 仓库膨胀 | 所有代码封装在 `data-platform/`，不修改 ai-assistant 现有服务，后续可整体迁出 |
